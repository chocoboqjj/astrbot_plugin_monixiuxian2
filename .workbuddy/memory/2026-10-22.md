## 排查「摆设玩法」并修复（v3.1.7，已完成）
用 Explore 子代理做了全量摆设审计（95 条命令 / handlers / managers / core / data / _conf_schema 37 个 key / migration 建表清单），再逐条手工核实。**核心发现：全新安装路径存在灾难级断链**。

**P0-A：全新安装缺 7 张表 + 2 个缺列（`data/migration.py`）**
- 根因：`migrate()` 全新安装分支走 `_create_all_tables_v2()` 后**直接写 `version=LATEST_DB_VERSION(20)` 并 return**，v12~v20 的 19 个迁移任务全部被跳过。
- 缺失表：`blessed_lands`/`spirit_farms`/`dual_cultivation`/`dual_cultivation_requests`/`spirit_eyes`/`bounty_tasks`/`combat_cooldowns` → 洞天/灵田/双修/灵眼/悬赏/决斗全线 `no such table`。
- 缺失列：`user_cd.extra_data`（v20 加，但秘境/历练 set_user_busy 写入与 get_extra_data 读取都依赖它 → 一进秘境就崩）、`spirit_eyes.last_collect_time`（v16 建表无、v20 才 ALTER）。
- 种子数据：`rifts` 5 条默认秘境在 v15 迁移中 → `/秘境列表` 恒空。
- 修复：在 `_create_all_tables_v2()` 内补齐全部 7 张表建表语句 + 秘境/灵眼种子数据 + `user_cd.extra_data` 列 + `spirit_eyes.last_collect_time` 列。**注意：v14/v16/v20 迁移保持原样不动**，以兼容存量库。

**P0-B：商店 7 个配置全部失效（`core/shop_manager.py`、`handlers/shop_handler.py`）**
- 根因：`_conf_schema.json` 的 `VALUES` 是**嵌套对象**（`type:object` + `items`），实际值在 `config["VALUES"][key]`；但商店代码写 `self.config.get("X", 默认)` 读**顶层** → 永远拿不到。
- 失效项：PAVILION_REFRESH_HOURS / PAVILION_PILL_COUNT / PAVILION_WEAPON_COUNT / PAVILION_TREASURE_COUNT / SHOP_DISCOUNT_MIN / SHOP_DISCOUNT_MAX / SHOP_STOCK_DIVISOR。
- 修复：两个类各加 `_get_value(key, default)`，优先读 `VALUES` 再退回顶层再回落默认（兼容老格式）。

**P1：假文案 / 空转数据**
- 洞天「修炼加成 +X%」三处文案与实际不符（`exp_bonus` 只在收取产出用，闭关零影响）→ 改为真正接入 `calculate_cultivation_exp(..., blessed_land_bonus)`；文案区分「闭关修炼加成」与「挂机产出」；挂机修为改按 `max_exp_per_hour` 固定发放，消除「以 player.experience 为基数」的复利膨胀。
- 传承系统对新玩家恒空：`create_player` 不写 impart_info/buff_info/user_cd，唯一写入点 `update_impart` 零调用 → 建号时初始化三表（`_init_player_related_tables`），`get_impart_info` 缺失时自愈补建，`create_impart_info`/`create_buff_info` 改 `INSERT OR IGNORE` 幂等。
- `set_user_busy` 纯 UPDATE → 记录不存在时静默失效，改 UPSERT。
- `database_extended.complete_bounty` 恒返回 True → 改为校验进度/时限 + 按实际结果返回。

**P1：宗门任务锁死玩家 1 小时（`managers/sect_manager.py`）**
- 根因：宗门任务用 `set_user_busy(type=4)` 占用忙碌状态，而忙碌状态会封锁除签到/银行外的**所有**指令。
- 修复：改用 `system_config` 存独立冷却（`sect_task_cd_{uid}`），不动忙碌状态；`sect_task` 字段从死数据改为每日任务计数（上限 3 次）。

**新增玩法：宗门建设（丹房）**
- 宗门资材从「只增不消费」变为可消费：5 阶丹房，资材 + 灵石升级；丹房等级决定弟子每日可领丹药种类；新增 `宗门建设`/`宗门丹房`/`宗门丹药` 三条指令 + `_schedule_sect_daily_reset` 每日 0 点重置。
- `SHOP_MANAGERS` 配置不再空转：新增「刷新商店」管理员指令。

## 解除指令互锁 · 活动可并行（v3.1.8，已完成）
**根因**：`user_cd` 表是**单行单 type** 设计，三种活动（闭关/历练/秘境）共用一个槽位 → ① 互相覆盖（开历练会冲掉闭关状态，闭关时长丢失）；② `player_required` 检测到「忙碌」就封锁几乎所有指令；③ 另有 8 处 handler/manager 重复做全局互斥，把炼丹/打Boss/决斗/宗门/双修这些**瞬时操作**也拦了。

**方案**：
- 新增 `core/activity_manager.py::ActivityManager` + `user_activity` 表，主键 `(user_id, activity_type)`，三种活动各占一行独立计时。
  - 接口：`start(user_id, type, scheduled_time, extra_data, create_time=None)` / `finish` / `get` / `get_all` / `active_types` / `is_active` / `is_any_active` / `migrate_legacy`。
  - `start` 的 `create_time` 参数用于迁移旧数据时保留原始开始时间（否则时长会丢）。
- `db.activity_mgr` 注入（与 `db.penalty_mgr` 同款惯用法），各 manager 用 `getattr(self.db, "activity_mgr", None)` 取用；**未注入时降级到旧 user_cd 语义**。
- `handlers/utils.py`：`player_required` **彻底移除**忙碌检查与「修炼中」检查；删掉死代码 `BUSY_STATE_ALLOWED_COMMANDS` + `_is_command_allowed()` + `UserStatus` 导入。新增 `get_active_activity_names(db, uid)` 辅助。
- 改造点：`player_handler`（闭关/出关/弃道重修）、`adventure_manager`（start/finish/status）、`rift_manager`（enter/finish/exit），三者各自只清自己的槽位。
- 移除全局互斥的 8 处： alchemy_handlers / alchemy_manager / boss_manager / combat_handlers(×2) / sect_handlers(×4) / dual_cultivation_manager(×2)。顺带清掉 7 个文件里变成未使用的 `UserStatus` 导入。
- 「我的信息」新增「进行中的活动」面板（`_build_activity_panel`），显示每项活动已用时/剩余时间。
- `delete_player_cascade` 补 `DELETE FROM user_activity`。
- 启动时 `_migrate_legacy_activities()` 把旧 `user_cd` 状态迁移到新表。

**结果**：闭关/历练/秘境**可同时进行**且**不限制任何其他指令**；只有同类重复启动被拒。弃道重修仍要求结束活动（数据安全，非玩法互锁）。

**验证**：新增 `test_parallel_activity.py`（22 项断言全通过）；此前 5 组测试复跑全通过，共 74 项断言。

## 排查「物品形同虚设」→ 发现并修复储物戒 lost update（v3.1.9）
**用户问**：有没有物品/道具只能获取但没地方使用？

**排查结论（两层问题）**：
1. **表面层（物品经济断裂）**：
   - `config/items.json` 14 种材料**全部零消费出口**（商店会卖，买了只能干看）
   - 掉落表产出的 10 种物品（灵草/玄铁/星辰石/灵兽毛皮/灵兽内丹/功法残页/秘境精华/天材地宝/灵石碎片/妖兽精血）**在任何配置文件里都没有定义**——两套命名体系并存
   - 炼丹配方消耗「灵草」而 items.json 里叫「百年灵草」→ 名字对不上
   - 设计专家测算：当前 5 个炼丹配方**每一个都是净亏损**（灵石成本=产出满额售价×成功率折扣），玩家最优解是"种田+吃商店丹药"，炼丹系统被完全绕过 → 这才是材料堆积的真正原因
   - 灵田收获产出的是**同名作物**（`spirit_farm_manager.py:179` 存作物名进储物戒），不是修为灵石
   - items.json 的 10 种功法**无 equip_effects/exp_multiplier 字段** → 装备后是全零空壳；`镇魂幡`/`戮仙剑阵` 是 accessory 类型，装备逻辑未实现
   - items.json 的 10 种法器数值被 weapons.json 全面碾压（如 弑神枪攻500/999万灵石 vs 霸王帝刀物伤850+法伤500/23.6万灵石）
2. **底层（真 bug，比物品问题严重得多）**：**储物戒 lost update，10 处**。

**lost update 根因**：`core/storage_ring_manager.py` 的 `store_item`/`retrieve_item`/`discard_item` 内部 `player = await self.db.get_player_by_id(...)` **局部重绑定**。Python 传参是引用传递但重绑定不影响调用方 → 调用方的 player 永远是旧快照 → 其后的 `update_player()`（43 字段全量 UPDATE）把刚做的 storage_ring_items 变更**覆盖回旧值**。

**10 处缺陷点**：
| 文件 | 后果 |
|---|---|
| `handlers/equipment_handler.py:136` → `equipment_manager.py:192` | **可无限复制装备**（剑同时在装备栏和储物戒） |
| `handlers/shop_handler.py:265` → `:286` | **商店白花钱**（钱扣了物品没进包） |
| `managers/rift_manager.py:247` → `:260` | 秘境掉落全丢 |
| `managers/adventure_manager.py:440` → `:236` | 历练掉落全丢 |
| `managers/boss_manager.py:245` → `:290` | Boss 掉落全丢 |
| `managers/alchemy_manager.py:214` → `:236/267` | 炼丹材料不扣（提示说扣了，实际没扣） |

**修复（方案 A，改动最小）**：
- `core/storage_ring_manager.py` 新增 `_sync_ring_items_to_caller(caller_player, fresh_player)`，三个方法**成功提交后**把最新戒指内容同步回调用方对象；失败路径不同步。
- 三个方法内部变量重命名 `fresh_player` 消除遮蔽，容量校验用 fresh_player。
- `data/data_manager.py::update_player` 加 `commit: bool = True`；`external_transaction=True` 时传 `commit=False`（修复商店外层事务 rollback 失效——实测外层 rollback 后 gold 仍是 777）。
- `retrieve_item`/`discard_item` 补 `external_transaction` 参数。

**另修**：`handlers/shop_handler.py:228` 用 `self.STORAGE_ITEM_TYPES` 访问**模块级常量**（类体无此属性）→ 必抛 AttributeError → **商店购买对任何物品都崩溃**。改为 `STORAGE_ITEM_TYPES`。

**验证**：新增 `test_lost_update_fix.py`（44 项断言：10 个缺陷点修复 + 8 个安全点无回归 + 事务回滚）；7 组测试共 139 项断言全通过。

**关键踩坑**：`handlers/utils.py` 导入 `models_extended` 会触发循环导入（config_manager→data→migration→config_manager）；测 `ShopHandler` 需要 mock `astrbot.api.event` / `astrbot.api.all` 且 `astrbot`/`astrbot.api` 必须 `__path__=[]` 才是真 package。
